# MCP App 插件开发与宿主接入

本指南用于开发需要交互界面的 OpenClaw 扩展，重点是让界面在宿主中正确显示，并保留可信的应用身份、会话归属和打开来源。普通工具、Hook 或 Skill 插件无需实现 MCP App。

开发环境沿用[开发指南](README.md)。本仓库匹配 OpenClaw 2026.10.4 公开 SDK，MCP Apps SDK 版本由根目录 `package.json` 和锁文件确定。完成实现后使用[接入 checklist](mcp-app-checklist.md)逐项验收。

## 1 先确定需要的能力

| 能力                 | 是否必需         | 实现范围                                                       |
| -------------------- | ---------------- | -------------------------------------------------------------- |
| 插件加载与 MCP 可用  | 必需             | 有效清单、扩展入口、MCP 声明及当前策略许可                     |
| 身份和来源校验       | 必需             | 使用原生身份与会话绑定，区分真实打开路径，保持沙箱边界         |
| 聊天工具结果显示界面 | MCP App 基础能力 | 工具 UI 元数据、HTML 资源及标准 App 通信                       |
| 手动启动入口         | 按需             | 提供可直接启动的工具，按公开协议声明 `thread` 或 `global` 范围 |
| 应用图标             | 按需             | 在工具或服务的 `icons` 中声明内嵌图片                          |
| 文件预览             | 按需             | 声明 `file` 入口、支持的扩展名及文件访问约束                   |
| 上下文同步与继续修改 | 按需             | 同步当前内容；读写指定实例时校验对象身份和内容代次             |
| 持久保存与重启恢复   | 按需             | 定义存储、冲突和恢复范围，不重放原业务调用                     |

`_meta.ui`、标准 App 初始化和 AppBridge 属于 MCP Apps 接入。`_meta['openai/ui'].entrypoints` 是本指南使用的 OpenClaw 入口扩展。额外文件写回或内容关联适配需明确协议与支持版本，不能视为所有 MCP 客户端都会提供的能力。本指南只描述插件需要声明、处理和验证的部分。

仅需显示一段交互结果的插件，不必同时建设文档库、连续编辑、文件写回或历史版本系统。手动入口也可以是唯一的业务使用入口；其界面协议仍与聊天工具结果相同。

## 2 让扩展和服务能独立运行

每个插件位于 `plugins/<name>/`。在 `openclaw.plugin.json` 声明稳定的扩展 ID 和 MCP 服务，在 `package.json` 的 `openclaw.extensions` 指定实际交付的扩展入口。例如：

```json
{
  "id": "sample-app",
  "name": "Sample",
  "enabledByDefault": false,
  "mcpServers": {
    "sample": { "command": "node", "args": ["./dist/server.cjs"] }
  },
  "configSchema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {}
  }
}
```

```json
{
  "name": "@local-mcp/sample-app",
  "version": "0.1.0",
  "openclaw": { "extensions": ["./dist/extension.cjs"] }
}
```

以上是清单和包信息的最小示意；实际包仍需声明适用的模块类型、交付文件和依赖。扩展入口声明的 ID 必须与清单一致，生成的入口、服务及资源必须进入交付包。

由原生加载器解析相对路径并管理 MCP 进程，不写死开发机目录，不要求用户再手工配置同名服务。stdio 的标准输出只用于 MCP 协议，运行日志写入标准错误。工具参数通过 schema 校验，实际会写入数据的工具如实声明行为；annotations 和 App-only 可见性都不能替代授权。

服务自身不需要持有宿主登录凭据。原生扩展增加 Gateway 接口时，按匹配 SDK 声明所需 contracts，并使用认证请求上下文。不要将 SDK 或下游宿主源码复制进交付包。

## 3 让界面正常显示

### 工具声明和资源响应

希望执行后显示界面的工具声明一个真实可读取的 UI 资源：

```json
{
  "name": "create_view",
  "description": "Create an interactive view from the supplied data.",
  "inputSchema": {
    "type": "object",
    "properties": { "title": { "type": "string" } },
    "additionalProperties": false
  },
  "_meta": { "ui": { "resourceUri": "ui://sample/app.html" } }
}
```

`resources/read` 对该 URI 返回 HTML，且 URI 和 MIME 一致：

```json
{
  "contents": [
    {
      "uri": "ui://sample/app.html",
      "mimeType": "text/html;profile=mcp-app",
      "text": "<!doctype html><html>...</html>"
    }
  ]
}
```

HTML 中需包含实际构建的界面和初始化逻辑，不能直接使用示例占位内容。工具成功结果使用 `structuredContent` 返回界面需要的数据或引用；失败返回 `isError: true` 及可理解的原因。仅在文本里返回 SVG、HTML、XML 或本地文件路径，不会自动获得 MCP App 展示。

原生视图描述由宿主根据真实工具执行或手动启动生成。插件不伪造 `viewId`、工具调用记录、Canvas 短码或预览 descriptor，也不通过助手正文要求宿主授予界面权限。

### 前端初始化

使用 `@modelcontextprotocol/ext-apps` 的 `App`，先安装处理器，再连接宿主。接收工具结果、解析业务数据后挂载或更新界面；初始化、读取和渲染失败应在 App 内提供清晰状态。`shared/ui.ts` 是本仓库的实际示例。

下面的前端入口展示最小通信顺序；业务编辑器可以替换结果显示区域：

```ts
import { App } from '@modelcontextprotocol/ext-apps';

const output = document.createElement('pre');
document.body.append(output);
const app = new App({ name: 'Sample', version: '0.1.0' }, {});

app.ontoolresult = result => {
  output.textContent = JSON.stringify(result.structuredContent ?? {}, null, 2);
};

void app.connect().catch(error => {
  output.textContent = `应用初始化失败：${String(error)}`;
});
```

App 调用工具和读取资源时使用 SDK 的 `callServerTool`、`readServerResource` 等标准接口。先检查调用是否成功，再解析 payload；不把原生权限错误误报为 JSON 或界面解析错误。只使用宿主实际公告的能力，不假设下载、上下文同步或额外 RPC 一定存在。

工具结果只读展示也必须经过原生准入。界面能显示、MCP 连接测试成功、目录显示应用标签是不同状态，不能相互替代。

## 4 身份和来源必须可信

身份回答“这是哪个应用实例、属于谁”；来源回答“这次实例如何创建或打开”。插件从真实准入和认证请求核验这些事实，界面显示状态不能改写来源或授予权限。

| 信息                                      | 权威来源及用途                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| 扩展 ID 与 MCP 服务名                     | 原生插件清单和当前 MCP 归属，用于识别真正提供服务的扩展；显示名称不能代替  |
| 工具、UI 资源、工具调用 ID                | 原生实际执行或启动结果，用于把界面对应到确切调用                           |
| 原生 `viewId`                             | 宿主准入的视图引用；可见的 ID 本身不是工具或文件授权                       |
| `sessionKey`、`sessionId`、助手与当前连接 | 认证会话及请求上下文，用于隔离会话实例、连接代次与权限                     |
| 打开来源                                  | 宿主实际执行的聊天工具调用、手动启动或文件打开流程，移动界面不改写它       |
| 业务文档 ID 与 revision                   | 处理可修改对象时由插件管理，用于区分同名文档、检测过期写入；不替代原生授权 |

### 使用标准宿主时

宿主负责认证 Gateway 连接、核对原生预览和会话归属、建立 AppBridge，并随会话或连接变化撤销旧交互。插件通过标准桥运行，不另建携带宿主凭据的连接，不在 HTML 中存放宿主访问凭据，也不自行从窗口 URL、标题、最后一条消息或 XML 字段猜会话身份。

宿主集成必须区分三种真实来源：

| 来源               | 实例从哪里取得                   | 接入注意事项                                 |
| ------------------ | -------------------------------- | -------------------------------------------- |
| 聊天上下文中的 App | 确切工具结果及其原生视图         | 不从助手正文中的链接或伪造描述恢复权限       |
| 手动启动的 App     | 原生手动入口执行后返回的视图     | 不能因为服务同名就改用聊天中的另一实例       |
| 点击文件打开的 App | 当前文件入口和宿主签发的资源     | 文件路径、文件名和业务文档 ID 都不是访问凭据 |

插件依据真实执行来源、业务内容身份和认证绑定处理请求，展示位置不改变这些事实。插件不推断界面位于消息、侧栏还是其他窗口，也不因位置变化重新执行创建工具。

### 插件增加自己的原生接口时

文件预览、源文件保存或当前画布修改等接口，需要在标准桥之外继续承担授权责任：

1. 在认证请求上下文执行，核对调用者的当前权限；参数里的会话 ID 或 `operator.admin` scope 不能单独证明目标会话归属。
2. 用公开 SDK 重读当前会话，核对 session incarnation、生命周期及权限状态，并确认当前服务仍属于预期扩展；拒绝被同名自建服务覆盖的绑定。
3. 操作已打开视图时，从宿主已准入的不可变身份核对服务、工具、资源和视图。单独一次 `mcp.app.view` 读取不能被当作它未证明的服务来源凭据；需要来源证明时，按目标宿主约定通过该确切视图的原连接核验，不能换成静态目录或其他会话的 MCP 连接。
4. 文件或工作区操作使用原生当前解析出的工作目录和文件边界，不将助手 home 当作项目目录，也不改写会话继承字段来兜底。
5. 每次敏感读取或写入前，以及异步准备完成后，重新核验请求、连接、会话和授权仍有效；关闭、切换、过期及迟到回包不能恢复旧权限。

`plugins/univer/workspace-files.ts` 展示了文件能力的公开 SDK 接入。它不是所有 MCP App 都要复制的认证框架；普通 App 继续使用标准宿主即可。

业务数据可以按产品设计跨会话保存，例如本仓库的用户文档库。文档存储范围与原生视图的交互授权要分别定义；不能把跨会话文档 ID 当成跨会话调用或文件写入的许可。

## 5 按需增加手动入口和图标

### 手动启动入口

提供手动启动能力时，声明一个可直接启动的入口工具，按 OpenClaw 公开协议选择 `thread` 或 `global` 范围。下面的例子声明 `global`：

```json
{
  "name": "open_editor",
  "title": "Sample",
  "description": "Open the application without a model request.",
  "inputSchema": {
    "type": "object",
    "properties": {},
    "additionalProperties": false
  },
  "_meta": {
    "ui": {
      "resourceUri": "ui://sample/app.html",
      "visibility": ["app"]
    },
    "openai/ui": { "entrypoints": [{ "type": "global" }] }
  }
}
```

`visibility: ['app']` 避免手动启动工具进入模型目录；入口能力由 `entrypoints` 声明。工具需能用空参数启动，并实际返回供同一 UI 消费的结果。仅在工具结果展示界面时，可以不提供此工具。

插件只声明入口能力、参数 schema 和真实工具结果，不规定入口呈现位置。检查实际 MCP 发现结果中是否保留了这些元数据；启动失败或结果未知时，不通过再次执行业务工具来伪造成功。

### 图标

在 MCP 服务信息和工具的顶层 `icons` 中声明图标，不放在工具返回正文或自行添加的 manifest 字段里：

```ts
const icons = [
  {
    src:
      'data:image/svg+xml,' +
      encodeURIComponent(
        '<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 32 32"><rect width="32" height="32" rx="6" fill="#2563eb"/></svg>',
      ),
    mimeType: 'image/svg+xml',
    sizes: ['32x32'],
  },
];
```

可分别声明 `theme: 'light'`、`theme: 'dark'`，或不带 theme 提供通用版本。离线交付使用体积受控的内嵌 `data:image/...`，图片格式和大小满足接入协议约束；不使用公网地址或 `file://`。验证图片可解码、主题版本齐全，以及构建后的服务仍返回实际图标元数据。

本仓库 `shared/server.ts` 已提供 global 和文件入口元数据，当前没有统一声明服务或工具 `icons`。需要自定义图标时应显式补充对应元数据，并验证构建后的真实目录。

## 6 按需增加文件和对话协作

### 文件入口

打开文件的工具保持 App-only，元数据示例：

```json
{
  "ui": {
    "resourceUri": "ui://sample/app.html",
    "visibility": ["app"]
  },
  "openai/ui": {
    "entrypoints": [{ "type": "file", "extensions": [".sample"] }]
  }
}
```

此对象放入工具的 `_meta`，工具 schema 接受原生传入的 `file` 对象。原生文件入口传递文件名及视图绑定的 `openclaw-file://` 资源，由 App 通过标准桥读取，不能让 MCP 进程按任意路径打开本机文件。插件仅处理声明支持的文件类型与合法资源。

需要更大的快照或源文件写回时，可实现宿主支持的 `mcp-app-files.open.<serverName>` 和 `mcp-app-files.resource.<serverName>` 约定。它们是额外适配，不是所有 MCP App 的必需项。文件大小、格式、路径边界、视图权限、ETag 冲突、备份和写入回执由插件负责；源文件写回不等于通过保存对话框导出。

### 上下文同步和当前内容修改

需要模型理解 App 当前内容时，先检查宿主公告的 `updateModelContext` 能力，再同步有界内容或引用。同步成功不代表文件已经保存，也不会自动发起模型回复。App 发起后续消息时沿宿主确认与草稿流程，由用户发送。

需要发送前取得未保存编辑时，按宿主支持的 App 工具约定声明 `_meta['workspace/prepare-context'] = true`，提交正在输入的文字、取得快照并等待同步完成；没有实现此可选约定，就不能承诺快速发送包含未保存内容。本仓库当前上下文只提供文档身份、版本等摘要，不等于完整编辑快照或通用画布修改接口。

需要模型继续修改同一文档时，另行实现确切业务对象的读写工具：明确引用优先，其次使用宿主在发送时绑定的实例，歧义时询问；应用前核对内容代次，保留并行手改，一次修改尽量对应一次撤销。只有实际应用回执才能确认当前界面已更新；修改数据库成功不能直接证明未保存的界面内容已改变。不要为修改再创建重复编辑器，也不默认要求建设历史版本库。

### 展示环境变化

插件通过标准 host context 处理尺寸、主题和展示模式变化，更新必要的布局与样式，保留当前业务对象、未提交输入和插件自身的撤销／筛选状态。重复或等价通知保持幂等，不重新加载初始内容、重建编辑器或执行创建工具。

界面放置、标签管理和窗口组织由宿主处理，不要求插件声明新的展示位置协议。插件依据已认证的业务对象和原生绑定处理请求，不从父节点、窗口标题或 URL 推断当前会话和授权。

### 可选的内容关联和历史回执

需要多个工具结果指向同一内容，或在历史刷新后保留“已更新”反馈时，再与目标宿主约定受审查的关联适配。普通查看器不必实现它，已有文档库也不因此需要增加版本库。建议明确以下信息及权威来源；字段名称和传输结构属于该集成约定，不是新的 MCP Apps 标准：

| 信息 | 要求 |
| ---- | ---- |
| 来源命名空间与内容 ID | 从真实插件／服务／UI 资源及认证会话核对来源；插件签发稳定业务 ID，新建另一内容使用新 ID |
| 标题与原视图关联 | 标题只供显示；原视图关联必须能追溯到实际准入，不能用新恢复 viewId 覆盖原始来源 |
| 操作及确认状态 | 精确关联实际工具调用；只有收到真实应用 ACK 的更新才宣称界面已更新 |
| 原生会话与已知 run | 核对 agent、sessionKey、物理 sessionId 及当前绑定；有真实 run 身份时完全匹配 |

实时工具结果中的自定义 `details` 等字段可能被原生历史投影过滤；仅测完整模拟结果会漏掉“更新卡片短暂出现后消失”。需要持久定位时，在原生实际保留的结果中使用有明确类型／版本和长度上限的紧凑关联记录，并用真实 Gateway 的历史响应验收。记录只包含标题、目标、操作和可核实来源，不复制 HTML、完整工作簿、文件字节、秘密或临时授权。完整业务结果继续使用插件已有存储路径，不能只依赖可能被过滤的字段来恢复它。

类型可以采用插件自有的 `<plugin>.content-reference.v1`，但这只是命名示意，任意同形 JSON 不会自动被宿主识别。宿主适配必须核对真实工具来源、精确 toolCallId 和来源链；已知 run 应按原生消息结构归一化后比较，不能拿显示层合成 ID 替代。助手示例、其他插件同名字段、失败／冲突／未知结果均不能产生成功引用。关联记录自身不是权限凭据，不能伪造 native descriptor、声明任意 RPC 方法或隐藏正常预览。

### 本地状态和恢复

当前输入、选区和撤销栈属于编辑器本地状态。插件在业务载荷变化时核对对象 ID 与内容代次，仅应用真实内容更新，保留并行手改。加载请求使用代次或取消机制拒绝旧结果，订阅和回调注册保持幂等，按标准关闭通知释放自身资源。

持久文档、已确认结果和未保存 UI 草稿具有不同恢复范围。恢复只读取插件已承诺保存的内容，不重放原业务工具、复用旧 token 或恢复旧工具授权。原业务内容身份与新恢复 viewId 分别保留；支持同内容恢复的接口应对并发读取去重，不能按每次历史操作另建业务对象。

手动／文件启动不保证出现在聊天工具历史中；需要恢复这类对象时，以自身可验证的原生准入和已确认结果为依据，不假定之前存在模型创建记录。只读恢复不注册旧编辑目标、不沿用旧消息／上下文／文件能力。后续写入须经过当前授权流程。支持原始结果、最新已确认内容还是已保存文档，以及未保存草稿是否能恢复，写入插件详细说明。

## 7 离线资源和交付

使用现有构建流程将 JS、CSS、WASM、Worker、字体及许可材料打入交付包。原生 UI HTML 有容量限制，大编辑器可由小型 UI wrapper 引用受限的本机资源；不要把完整编辑器塞进工具结果或聊天上下文。当前两个插件通过 `shared/assets.ts` 提供本机静态页面。

若需要 loopback 服务，只监听 `127.0.0.1`，限制 Host、精确路径和请求方法，不提供任意文件、配置读取或代理。发布 URL 和 CSP 前检查端口是否被 Chromium/WHATWG 禁止，例如 `6000`；操作系统分配成功不保证浏览器能访问。静态监听端口可以有界重新分配，不能为此重放业务工具。当前 `shared/assets.ts` 使用随机端口，尚未实现禁用端口筛选，复用它时需单独补齐并验证这一条件。

资源 `_meta.ui.csp` 仅放行实际需要的本机资源、frame 和连接来源。使用标准 AppBridge 保持宿主来源检查；自建内层 iframe relay 时核对确切 WindowProxy 和消息格式。opaque sandbox 必需的通配 target 只适用于已绑定的父子窗口，不能放宽为接受任意窗口消息。不要通过关闭沙箱或扩大公网 CSP 修复白屏。

按[离线构建与交付](offline-delivery.md)构建独立目录和压缩包。核对源码、生成资源、原生入口和最终安装包一致；包内完整性清单只能检测文件完整性，不能证明发布者身份。新增插件同步更新构建与打包名单、插件说明和文档导航。

## 8 验证与故障定位

从仓库根目录执行已有命令，修改源码后先构建，再运行服务和浏览器测试：

```sh
npm run check
npm run build
npm test
npm run test:ui
npm run pack:apps
```

这些命令的范围见[测试与验收](testing.md)。通用服务测试验证元数据、资源和结果；浏览器测试验证真实界面。认证接口、入口元数据和资源权限还必须在匹配版本的 OpenClaw 环境中验证。纯文档修改执行 `git diff --check`，无需重建插件。

| 现象                       | 优先核对                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| 启动工具未被发现           | 核对构建后真实 MCP 目录中的 entrypoints、工具可见性、扩展与服务启用及当前工具策略 |
| 图标资源无效               | 核对实际工具／服务 icons、图片解码、大小限制和主题版本 |
| 有卡片但界面白屏           | UI MIME、SDK 初始化、真实子资源、CSP、端口、资源完整性和实际安装版本                                 |
| 出现不可用预览             | 工具是否明确失败、视图是否过期、原生身份是否匹配；不能靠隐藏所有预览规避                             |
| 继续对话后旧 App 不可用    | 当前连接和会话归属、手动 App 与模型是否使用同一原生工作目录、资源服务是否仍存活                      |
| 权限读取失败被报成解析错误 | 先检查 RPC 成功状态，再解析 payload；仅对明确可重试的只读准入失败有限等待，并重新核验 owner          |
| 切换回来修改丢失           | iframe 是否被重载、复用时是否误读初始内容、是否把暂停当成销毁                                        |
| 更新提示短暂出现后消失     | 对比实时结果与真实历史响应，确认紧凑回执未随自定义 details 被过滤；不以隐藏提示作为修复              |
| 历史刷新后重复打开编辑器   | 原内容与恢复 viewId 是否分开关联，同内容恢复是否去重；不按每次 operationId 创建实例                   |
| 环境通知后输入或撤销丢失   | 检查处理器是否误加载初始内容、重建编辑器或重复执行业务工具 |
| 模型读到旧内容             | 上下文能力是否公告、同步是否确认、输入是否提交、目标是否为同一实例                                   |

普通 App 使用公开 SDK 和标准宿主即可。发现原生目录、租约或身份问题时，交由对应宿主修复；不要在插件中导入私有模块、篡改会话事实、创建第二套聊天记录或依赖特定下游补丁。未知发送、启动和写入不自动重放。
